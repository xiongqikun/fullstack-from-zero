# Research brief: github-collab-ci

Topic: collaboration and automation on GitHub for a beginner who may not have an account yet.
Researched 2026-11-19 on the reference Mac (plan G7) (macOS 27.2 arm64, zsh, git 2.54.0 Apple Git, uv 0.13.5). No account, credential, push or global install was used.

Tags: **[local]** = I ran it here today. **[source: URL]** = read in a primary source today. **[memory]** = not verified today.

## 1. Findings that should change the course design

1. **`git commit` can fail on a Mac with a half-written global signing config.** If the global `~/.gitconfig` has `commit.gpgsign=true`, `gpg.format=openpgp`, `gpg.program=gpg`, an empty `user.signingkey`, and no `gpg` binary exists on PATH, in `/opt/homebrew/bin` or `/usr/local/bin`, the very first commit dies with `error: cannot run gpg: No such file or directory` / `fatal: failed to write commit object` [local, reproduced in a throwaway repo]. Such a key set (with `gpg.ssh.program`, `gpg.ssh.allowedsignersfile`, `tag.forcesignannotated`, `core.excludesfile=~/.gitignore_global`) can be left behind by a Git GUI. The repo-local workaround is `git config commit.gpgsign false`; it does not touch the global file. Lesson 1 must check for this before anything else (see 7.6).
2. **Every action version in tutorials older than about six months is stale.** Today: `actions/checkout` v7.0.1, `actions/setup-python` v7.1.0, `astral-sh/setup-uv` v10.3.3, `actions/cache` v6.1.0, `actions/upload-artifact` v7.0.2, `actions/download-artifact` v8.0.2 [local, via API]. My own memory said checkout v5/v6 and setup-uv v7.
3. **`astral-sh/setup-uv@v10` does not exist.** Since v8.0.0 (2026-03-29) setup-uv publishes no major or minor tags; only full versions (`@v10.3.3`) or a commit SHA resolve. `commits/v10` returns HTTP 422, while the old `v7` tag still resolves to an old commit [local, via API]. A learner who "bumps the number" in an old snippet gets a broken workflow or a silently ancient action.
4. **The uv docs now pin every action by full commit SHA** with the version in a trailing comment, and call pinning the uv version itself "best practice" [source: https://docs.astral.sh/uv/guides/integration/github/, page dated 2026-11-17].
5. **A free personal account with a private repository cannot enforce anything.** Protected branches, rulesets, required status checks, CODEOWNERS, auto-merge, draft PRs, environments, wikis, Pages, secret scanning and push protection all need a public repository or a paid plan (section 4.1). CI still runs and shows red or green; it just cannot block a merge.
6. **Actions allowance is now expressed in dollars.** GitHub Free includes "$12 USD of included compute usage per month" for private repositories [source: GH/get-started/learning-about-github/githubs-plans]; a standard Linux runner costs $0.006 per minute, so $12 is about 2,000 Linux minutes. Public repositories stay free. Without a payment method on file, usage is simply blocked when the allowance is used up [source: GH/billing/concepts/product-billing/github-actions].
7. **Dependabot supports uv today** (`package-ecosystem: "uv"`, version and security updates, private repositories) [source: GH/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories].
8. **Workflow dependency lockfiles** (`.github/workflows/actions.lock`, generated by `gh actions-lock`) went GA on 2026-10-28 and GitHub now calls them better than SHA pinning. Too new and too gh-dependent for a beginner; awareness only (3.5).
9. **A fresh Mac usually has no `gh` and no SSH key** (`~/.ssh/*.pub` is empty). Apple Git already ships `credential.helper=osxkeychain` and `init.defaultBranch=main` in Xcode's bundled gitconfig, so `git init` creates `main` with no extra configuration [local].
10. **`uv init` copies the Git identity (name and e-mail) into `pyproject.toml` `authors`** [local]. On a public repository that publishes the e-mail address. Check it before the first push.

What the major bumps were about [source: release notes via API]:
- checkout v5 and v6, setup-python v6, cache v5, upload-artifact v6: Node 24 runtime. checkout v6 stores persisted credentials in a separate file under `$RUNNER_TEMP`. checkout v7 refuses fork PR code under `pull_request_target` / `workflow_run` unless `allow-unsafe-pr-checkout: true`, and moved to ESM. On 2026-07-20 that change was back-ported as a "[BREAKING]" minor release of every older major (v6.1.0, v5.1.0, v4.4.0, v3.7.0, v2.8.0): a real case of behaviour changing underneath a "stable" major line, useful for the tag-versus-SHA lesson.
- setup-python v7 removed the `pip-install` input. cache v6 and upload-artifact v7 are ESM migrations; upload-artifact v7 adds single-file unzipped uploads (`archive: false`).
- setup-uv v8: immutable releases, no major/minor tags. v9: `prune-cache` default became `false`. v10: with the default `enable-cache: auto`, caching is disabled for `pull_request_target`, `workflow_run`, `release` (and tag pushes); adds `version: latest-known`.
- Even official examples lag: the GitHub workflow-syntax page still shows `actions/checkout@v6` and `actions/cache@v4`, the setup-uv README shows `actions/checkout@v5`, the release-please README shows `@v4`. Old majors keep working; they are just not current.

### 3.2 setup-uv v10.3.3 inputs that matter [source: `action.yml` at tag v10.3.3, fetched via API]

- `version`: default empty, meaning "the `required-version` from `uv.toml` / `pyproject.toml`, else latest".
- `python-version`: sets `UV_PYTHON` for the rest of the job and overrides `.python-version` and `requires-python` pins.
- `enable-cache`: default `"auto"` = on for GitHub-hosted runners, off for self-hosted and for the sensitive events above. No extra `actions/cache` step is needed.
- `cache-dependency-glob`: default already covers `**/uv.lock` and `**/pyproject.toml`.
- `prune-cache`: default `"false"`. `activate-environment`: default `"false"` (use `uv run`).

### 3.3 The uv docs recipe [source: https://docs.astral.sh/uv/guides/integration/github/]

- Install with `astral-sh/setup-uv` pinned by SHA, pin the uv version with `version:`.
- Python: `uv python install` respects the project pin; `actions/setup-python` with `python-version-file: ".python-version"` "can be faster"; for a matrix set `python-version: ${{ matrix.python-version }}` on setup-uv (or `UV_PYTHON` without the action).
- `uv sync --locked --all-extras --dev`, then `uv run pytest tests`.
- Caching: `enable-cache: true`, or manual `actions/cache` keyed on `hashFiles('uv.lock')` plus `uv cache prune --ci`.
- Publishing: separate `build` and `publish` jobs so only `publish` has `id-token: write`; `environment: pypi`; `uv build`, then `uv publish` with Trusted Publishing; trigger on `v*` tags; `persist-credentials: false` on checkout.

### 3.4 Recommended `ci.yml` (validated here)

File: `artifacts/dot-github/workflows/ci.yml`. Every command in it was run locally in `demo/` and passed [local].

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

# Least privilege: the automatic GITHUB_TOKEN may only read the repository.
permissions:
  contents: read

# A newer push to the same branch or pull request cancels the older run.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  quality:
    name: Lint, format, types
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - name: Check out the repository
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false

      - name: Install uv
        uses: astral-sh/setup-uv@68559e99cc807c1eb7e9238fd43a15bba460eec2 # v10.3.3
        with:
          version: "0.13.5"

      - name: Install dependencies exactly as locked
        run: uv sync --locked

      - name: Lint
        run: uv run ruff check .

      - name: Check formatting
        run: uv run ruff format --check .

      - name: Type check
        run: uv run mypy

  test:
    name: Tests (Python ${{ matrix.python-version }})
    runs-on: ubuntu-latest
    timeout-minutes: 15
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.12", "3.13", "3.14"]
    steps:
      - name: Check out the repository
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false

      - name: Install uv and select Python ${{ matrix.python-version }}
        uses: astral-sh/setup-uv@68559e99cc807c1eb7e9238fd43a15bba460eec2 # v10.3.3
        with:
          version: "0.13.5"
          python-version: ${{ matrix.python-version }}

      - name: Install dependencies exactly as locked
        run: uv sync --locked

      - name: Run tests
        run: uv run pytest
```

Why each choice (all checkable in the sources above):
- `push` limited to `main` plus `pull_request`: `on: [push, pull_request]` runs everything twice for every push to a PR branch. `pull_request` with no `types` fires on `opened`, `synchronize`, `reopened` and tests the merge result, not only the branch head [source: GH/actions/reference/workflows-and-actions/events-that-trigger-workflows].
- `permissions: contents: read`: any permission not listed becomes `none` [source: GH/actions/reference/workflows-and-actions/workflow-syntax]. New personal repositories already default to a read-only token for `contents` and `packages` [source: GH/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository], but stating it makes the file safe wherever it is copied.
- `concurrency` with `${{ github.workflow }}-${{ github.ref }}` and `cancel-in-progress: true` is the docs' own example. Variant that never cancels runs on `main`: `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` (used in `ci-with-gate.yml`, validated).
- `persist-credentials: false`: checkout's default is `true`; zizmor flags the default as `artipacked` [local].
- `uv sync --locked`: fails instead of silently re-resolving when `uv.lock` is stale. `--dev` is on by default; add `--all-extras` only if the project defines extras.
- `timeout-minutes`: the default is 360 minutes, so a hung job would burn six hours of allowance [source: GH/actions/reference/workflows-and-actions/workflow-syntax].
- Matrix values are quoted strings; an unquoted `3.10` would be read as the number 3.1 [memory].

Local run of the same commands [local]:

```text
$ uv sync --locked                 -> exit 0
$ uv run ruff check .              -> All checks passed!
$ uv run ruff format --check .     -> 3 files already formatted
$ uv run mypy                      -> Success: no issues found in 2 source files
$ uv run pytest -q                 -> 2 passed in 0.00s
$ UV_PYTHON=3.14 uv sync --locked && UV_PYTHON=3.14 uv run pytest -q   -> 2 passed (python used: 3.14.9)
```

The failure a beginner will meet first, reproduced by hand-editing `dependencies` without re-locking [local]:

```text
$ uv sync --locked
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
hint: To update the lockfile, run `uv lock`.
```

Options worth mentioning, not teaching first:
- One source of truth for the uv version: `[tool.uv] required-version = ">=0.13.5,<0.14"` in `pyproject.toml` and drop `version:` from the workflow (setup-uv reads it). Checked locally: the lock stays valid, and a mismatch gives `error: Required uv version '==0.12.0' does not match the running version '0.13.5'` [local].
- Gate job for required checks: `ci-with-gate.yml` adds a `ci-ok` job with `if: always()` and `needs: [quality, test]` that fails unless both results are `success`. Require only "CI OK" so that changing the matrix never strands a required check (3.8).
- Cost control in a private repo: each job is billed rounded up to a whole minute [source: GH/billing/reference/actions-runner-pricing], so this file costs at least 4 minutes ($0.024) per run. Start with one Python version in private repositories and add the matrix later.
- Workflow keys that are new in 2026 and can be ignored by beginners: top-level and job-level `cache-mode` (`read` / `write` / `write-only` / `none`), `concurrency.queue: max`, step-level `background` / `wait` / `parallel` [source: GH/actions/reference/workflows-and-actions/workflow-syntax].

### 3.5 Pinning: tag, SHA or lockfile

- GitHub's secure-use page: the best measure is now a workflow dependency lockfile; for repositories that cannot adopt one, "Pin actions to a full-length commit SHA"; pin to a tag "only if you trust the creator" [source: GH/actions/reference/security/secure-use].
- Dependabot understands `uses: owner/repo@<sha> # v7.0.1` and updates both the SHA and the comment [source: GH/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories]. SHA pin plus Dependabot is therefore low-maintenance.
- Lockfile: `gh extension install github/gh-actions-lock`, then `gh actions-lock` writes `.github/workflows/actions.lock` and rewrites `uses:` lines to exact versions [source: GH/actions/how-tos/secure-your-work/lock-workflow-dependencies]. The GA changelog says it is available on "GitHub Enterprise Cloud, GitHub Enterprise Cloud with data residency, Team, and Free plans" [source: https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/], but the docs how-to page's product box still says only "GitHub Enterprise Cloud". The extension shipped v0.5.0 today. Not tested here.
- Teaching line: a tag is a name that can be moved; a SHA is a fingerprint that cannot. Chinese: "标签像名字，可以被改指向别人；哈希像身份证号，改不了。"

### 3.6 Runners, limits, billing

- Labels today: `ubuntu-latest` = `ubuntu-24.04` (`ubuntu-26.04` exists but is not `latest`), `macos-latest` = `macos-26` (arm64), `windows-latest` = `windows-2025`; a 1-CPU `ubuntu-slim` container runner exists for tiny jobs. Standard Linux runner: 4 CPU / 16 GB in public repositories, 2 CPU / 8 GB in private ones [source: GH/actions/reference/runners/github-hosted-runners].
- Per-minute rates: Linux 2-core $0.006, Linux 1-core slim $0.002, Windows $0.010, macOS $0.062 [source: GH/billing/concepts/product-billing/github-actions]. $12 buys about 2,000 Linux minutes or about 193 macOS minutes. Old tutorials say "2,000 minutes, macOS counts 10x"; the pricing page still shows "2,000 minutes/month" while the docs show dollars [source: https://github.com/pricing, read through a summarising fetch].
- Free plan storage: 500 MB artifacts (shared with Packages), 10 GB cache per repository, caches unused for 7 days are evicted [source: same billing page; GH/actions/reference/workflows-and-actions/dependency-caching]. Artifacts, logs and (since 2026-10-01) checks and run history are kept 90 days by default [source: GH/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository].
- Free plan concurrency: 20 jobs, 5 macOS [source: GH/actions/reference/limits].
- Hosted runner prices were cut on 2026-01-01; the announced $0.002 per minute charge for self-hosted runners is postponed [source: https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/].
- Caches written by a PR run are scoped to that PR; a `push` run on `main` is what seeds the cache other branches can read [source: GH/actions/reference/workflows-and-actions/dependency-caching].

### 3.8 Required status checks

- A check can be made required only through branch protection or a ruleset, so not on a Free private repository (4.1).
- Rules that surprise people [source: GH/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks]:
  - "A required status check must have completed successfully in the chosen repository during the past seven days" before it can be selected.
  - A workflow skipped by `paths:` or branch filters leaves a required check "Pending" forever. Do not put path filters on a required workflow.
  - A job skipped by its own `if:` reports "Success"; a job that depends on a failed job is skipped "and may not block merging". Hence the `if: always()` gate job.
  - Only runs triggered by `push`, `pull_request`, `pull_request_review`, `pull_request_target`, `deployment`, `deployment_status` count; a `workflow_dispatch` run does not satisfy a required check.
- Matrix jobs create one check per cell (`Tests (Python 3.12)` ...); renaming or removing a cell strands the requirement.
- "Strict" mode ("Require branches to be up to date before merging") is the default and forces a rebase or merge of `main` before every merge [source: GH/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches].

### 4.2 Fork or branch

- "Shared repository model": collaborators push topic branches to one repository; common for small teams and private projects. "Fork and pull model": copy the repository to your own account, push there, open a PR upstream; standard for open source [source: GH/pull-requests/reference/pull-requests].
- A fork of a public repository is public; a fork's visibility cannot be changed on its own [source: GH/pull-requests/reference/forks].
- For the learner's own project: always branches. Forks only when contributing to someone else's project.
- PRs from forks get a read-only token and no secrets, and the first run from a new contributor may wait for approval [memory]; checkout v7 blocks the dangerous `pull_request_target` pattern by default [source: release notes via API].

### 4.3 The pull request itself

- Draft PRs "cannot be merged, and code owners are not automatically requested to review them" [source: GH/pull-requests/reference/pull-requests]. `gh pr create --draft`, `gh pr ready` [source: CLI/gh_pr_create, CLI/gh_pr_ready]. Not available on Free private repositories (4.1).
- Description conventions (practice, not a GitHub rule): what changed, why, how it was tested, what to look at first, and `Closes #n`. A PR title in Conventional Commits form (`feat: add log return`) becomes the squash commit subject.
- Linking issues: keywords `close/closes/closed`, `fix/fixes/fixed`, `resolve/resolves/resolved`; `Closes #10`, `Fixes owner/repo#100`, repeat the keyword for each issue; "interpreted only when the pull request targets the repository's *default* branch"; also work in commit messages [source: GH/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue].
- PR template: `.github/pull_request_template.md` (also valid: repo root or `docs/`), must be on the default branch; several templates go in `.github/PULL_REQUEST_TEMPLATE/` and are chosen with a `template` query parameter [source: GH/communities/using-templates-to-encourage-useful-issues-and-pull-requests/creating-a-pull-request-template-for-your-repository].
- Issue templates: Markdown templates (`.md` with `name:` / `about:` front matter) or issue forms (`.yml`) in `.github/ISSUE_TEMPLATE/` on the default branch. Issue forms are still labelled "currently in public preview and subject to change". Required top-level keys: `name`, `description`, `body`; optional `title`, `labels`, `assignees`, `type`, `projects`. A label that does not exist in the repository is silently not applied. Body types include `markdown`, `input`, `textarea`, `dropdown`, `checkboxes` and `upload` [source: GH/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms].
- `config.yml` in the same folder: `blank_issues_enabled: false` and `contact_links` (`name`, `url`, `about`). With blank issues disabled, people with write access still see a "Blank issue" option [source: GH/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository].
- CODEOWNERS: file in `.github/`, root or `docs/` (first found wins); gitignore-like patterns then `@user` / `@org/team`; the last matching line wins; no `!` negation and no `[ ]` ranges; paths are case sensitive; owners need write access [source: GH/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners]. Pointless for a solo developer; one paragraph of awareness is enough.
- Labels: every new repository gets `accessibility`, `bug`, `documentation`, `duplicate`, `enhancement`, `good first issue`, `help wanted`, `invalid`, `question`, `wontfix` [source: GH/issues/using-labels-and-milestones-to-track-work/managing-labels]. `gh label create <name> --color <hex> --description ...` [source: CLI/gh_label_create]. Dependabot PRs use a `dependencies` label [memory].
- Milestones: a named group of issues and PRs with due date and completion percentage [source: GH/issues/using-labels-and-milestones-to-track-work/about-milestones].
- Reviews: decisions are Comment, Approve, Request changes. "Pull request authors cannot approve their own pull requests" [source: GH/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request]. So a solo developer must never require one approval. Copilot can be requested as a reviewer; on private repositories that consumes Actions compute and AI credits [source: GH/billing/concepts/product-billing/github-actions].
- Suggested changes: a reviewer proposes exact replacement lines; the author clicks "Commit suggestion" or batches several into one commit; suggesters become co-authors [source: GH/pull-requests/how-tos/review-pull-requests/incorporating-feedback-in-your-pull-request].
- Merge methods [source: GH/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github]:
  - Merge commit (default, `--no-ff`): keeps every commit plus a merge commit.
  - Squash and merge: one commit on `main`. Downside named by the docs: continuing to work on the same branch afterwards causes repeated conflicts, so delete the branch after merging.
  - Rebase and merge: replays commits without a merge commit; new SHAs; commits lose signature verification.
  - Recommended default for the learner: allow squash only, enable "Automatically delete head branches". `gh pr merge --squash --delete-branch` [source: CLI/gh_pr_merge].
- Auto-merge: merges when required reviews and checks pass; the button appears only when something is still blocking, so it presupposes branch protection [source: GH/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request]. `gh pr merge --auto --squash`.

### 4.4 Branch protection rules and rulesets

- Both protect branches, both can be active, all applicable rules are enforced. Rulesets layer (several can apply to one branch), can be disabled without deleting, are visible to anyone with read access, and can target tags [source: GH/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets]. For a new repository in 2026 teach rulesets and mention that older tutorials show "branch protection rules".
- Rules available: restrict creations / updates / deletions, require linear history, require signed commits, require a pull request before merging, require status checks to pass, block force pushes, plus scanning and file-restriction rules [source: GH/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets].
- "Require a pull request before merging": "The pull request doesn't necessarily have to be approved, but it must be opened." This is the solo-friendly setting: required PR, zero approvals, required check "CI OK", block force pushes, restrict deletions.
- `gh ruleset list | view | check` only read rulesets [source: CLI/gh_ruleset]; creating one is done in Settings > Rules > Rulesets or through the API.
- Push rulesets (file size, extension, path restrictions) need GitHub Team [source: same about-rulesets page].

### 4.5 A solo loop that works on a Free private repository

1. `gh issue create --title "..." --label enhancement`
2. `git switch -c feat/short-name`
3. Commit, then run the four checks locally.
4. `git push -u origin HEAD`, `gh pr create --fill` with `Closes #n` in the body.
5. `gh pr checks --watch` (exit code 8 means still pending) [source: CLI/gh_pr_checks].
6. Read your own diff in the browser, then `gh pr merge --squash --delete-branch`.
7. `git switch main && git pull`.

Nothing enforces steps 5 and 6 on a Free private repository; the lesson should say so plainly.

## 5. Releases

- A release is a Git tag plus notes plus optional files; GitHub attaches source zip and tarball automatically; up to 1000 assets, each under 2 GiB [source: GH/repositories/releasing-projects-on-github/about-releases].
- Auto-generated release notes list merged PRs, contributors and a full-changelog link. Categories come from PR labels through `.github/release.yml` (`changelog.exclude.labels`, `changelog.categories[*].title` / `.labels`, `"*"` as catch-all) [source: GH/repositories/releasing-projects-on-github/automatically-generated-release-notes]. They are built from PRs, so they reward the PR habit and do not need Conventional Commits.
- `gh release create v0.2.0 --generate-notes`; creates the tag if missing; `--verify-tag` aborts instead; `--draft`; `--notes-from-tag` [source: CLI/gh_release_create].
- Immutable releases (opt-in): after publishing, the tag cannot move and assets cannot change [source: GH/code-security/concepts/supply-chain-security/immutable-releases].
- Local pieces that work today [local]:

```text
$ uv version                          -> ci-demo 0.1.0
$ uv version --bump patch --dry-run   -> ci-demo 0.1.0 => 0.1.1
$ git tag -a v0.1.0 -m "v0.1.0" && git describe --tags   -> v0.1.0
$ uv build   -> dist/ci_demo-0.1.0.tar.gz and dist/ci_demo-0.1.0-py3-none-any.whl (uv writes its own dist/.gitignore)
```

  `uv version --bump` accepts `major, minor, patch, stable, alpha, beta, rc, post, dev` [local].

Changelog and version automation, from least to most magical:

| Tool (version today) | What it does | Verdict for a beginner |
|---|---|---|
| By hand: `CHANGELOG.md` + `uv version --bump` + `git tag -a` + `gh release create --generate-notes` | nothing hidden | **teach first** |
| GitHub generated notes + `.github/release.yml` | groups merged PRs by label at release time | **teach second**; zero tooling |
| git-cliff 2.14.2 | reads commits, prints a changelog; writes only with `-o` / `--prepend`; never commits, tags or pushes | least magical real tool. `uvx git-cliff` printed a grouped changelog for the demo repo and `--bumped-version` printed `v0.2.0` [local] |
| towncrier 26.9.0 | one small "news fragment" file per change, assembled at release; written for users, not from commit messages [source: https://towncrier.readthedocs.io/en/stable/] | honest but adds a per-PR chore; later |
| commitizen 4.19.4 | `cz bump` computes the bump from Conventional Commits, edits version files and changelog, creates the tag; `cz check` lints messages | works with `version_provider = "uv"`: dry run printed `bump: version 0.1.0 → 0.2.0`, `tag to create: v0.2.0`, `increment detected: MINOR` [local] |
| release-please (action v5.0.0) | bot keeps a "release PR" open; merging it tags and releases; `fix:` patch, `feat:` minor, `!` major; needs `contents`, `issues`, `pull-requests` write; PRs created with `GITHUB_TOKEN` do not trigger CI [source: https://github.com/googleapis/release-please-action] | team tool; skip |
| python-semantic-release 10.7.0 | in CI: decides version, stamps files, builds, commits, tags, pushes, creates the release [source: https://python-semantic-release.readthedocs.io/en/latest/] | most magical; skip |

Trusted publishing to PyPI (awareness only): PyPI trusts a specific repository + workflow + environment; the job presents an OIDC token and receives an API token that "expires 15 minutes after creation"; no long-lived secret is stored [source: https://docs.pypi.org/trusted-publishers/]. In the workflow: `permissions: id-token: write` on the publish job only, `environment: pypi`, `uv publish` (`--trusted-publishing automatic|always|never`, `--dry-run` exist [local]). Environments are unavailable on Free private repositories, which is fine because publishing to PyPI implies a public project.

## 6. Security features for a beginner

- Free for every repository: SECURITY.md policy, dependency graph, Dependabot alerts, Dependabot security updates, Dependabot version updates, malware alerts [source: GH/code-security/getting-started/github-security-features].
- Secret scanning: "Public repositories: Secret scanning runs automatically for free"; organisation-owned private repositories need paid Secret Protection; user-owned repositories only on Enterprise Managed Users [source: GH/code-security/concepts/secret-security/secret-scanning]. Push protection for users blocks known secret formats on pushes to public repositories and is on by default.
- So the learner's private repository has **no server-side secret guard**. Prevention is local: `.gitignore` for `.env`, a look at `git status` / `git diff --staged` before committing, optionally a local scanner in pre-commit [memory: gitleaks is the usual choice; not verified today].
- If a secret is pushed: revoke or rotate it first; that "may be sufficient". Rewriting history with `git-filter-repo` has heavy side effects [source: GH/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository]. Chinese: "先换锁，再考虑擦历史。"
- Dependabot and uv: YAML value `uv`, version updates, security updates, private repositories and private registries all "Supported". The "Supported versions" column says `v0.11` while the machine runs uv 0.13.5; whether that causes lockfile churn is untested. `pre-commit` and `github-actions` are also ecosystems. Version updates now wait a default 3-day cooldown; `cooldown.default-days` changes it [source: GH/code-security/reference/supply-chain-security/dependabot-options-reference].
- Validated example (`artifacts/dot-github/dependabot.yml`): two entries, `uv` and `github-actions`, `directory: "/"`, `schedule.interval: "weekly"`, `cooldown.default-days: 7`, one `groups` entry with `patterns: ["*"]` so each ecosystem produces one PR per week [local: schema ok, zizmor pedantic clean].
- Renovate: the `pep621` manager supports uv "including `uv.lock` files and `uv` workspaces" and `[dependency-groups]` [source: https://docs.renovatebot.com/modules/manager/pep621/]. More configurable, one more third-party app to install. Dependabot is built in; use it.
- SECURITY.md: root, `docs/` or `.github/`; states supported versions and how to report privately [source: GH/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/add-security-policy]. For a private solo project it is a two-line file; teach it as a convention.
- Commit signing: GitHub shows "Verified" for GPG, SSH or S/MIME signatures and says "SSH signatures are the simplest to generate"; setup is `git config --global gpg.format ssh` and `git config --global user.signingkey /PATH/TO/KEY.PUB`, then add the same public key to GitHub as a signing key [source: GH/authentication/managing-commit-signature-verification/about-commit-signature-verification and .../telling-git-about-your-signing-key]. Optional polish, but relevant because of finding 1.

## 7. Getting started safely

### 7.1 Account
- Sign up at github.com/signup with a verified e-mail; Google or Apple login is offered [source: GH/account-and-profile/how-tos/account-management/creating-an-account-on-github].
- 2FA is strongly recommended and becomes mandatory for accounts that contribute code (45-day enrolment window once selected) [source: GH/authentication/securing-your-account-with-two-factor-authentication-2fa/about-mandatory-two-factor-authentication]. Set it up on day one and save the recovery codes.
- E-mail privacy: Settings > Emails > "Keep my email addresses private" and "Block command line pushes that expose my email"; then use the GitHub-provided noreply address as `user.email` [source: GH/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address and .../blocking-command-line-pushes-that-expose-your-personal-email-address]. Changing `user.email` only affects future commits.

### 7.2 Authentication: three routes
- GitHub's own advice for HTTPS: "we recommend you use GitHub CLI or Git Credential Manager" [source: GH/get-started/git-basics/caching-your-github-credentials-in-git]. Account passwords no longer work for Git; a token is used instead [source: GH/get-started/git-basics/about-remote-repositories].
- **Route A, recommended: gh.** `brew install gh` (Homebrew and the release binaries are the two official macOS methods [source: https://github.com/cli/cli/blob/trunk/docs/install_macos.md]), then `gh auth login`: browser flow, choose HTTPS, answer yes to authenticating Git. The token is "stored securely in the system credential store" [source: CLI/gh_auth_login]. `gh auth status` checks it; `gh auth setup-git` re-registers gh as Git's credential helper.
- Route B, HTTPS without gh: Apple Git's `osxkeychain` helper is already active here [local], so the first push prompts for username and a personal access token and stores it in Keychain. Creating and pasting a token is the fiddly part for a beginner.
- Route C, SSH: `ssh-keygen -t ed25519 -C "email"`, `~/.ssh/config` with `AddKeysToAgent yes`, `UseKeychain yes`, `IdentityFile ~/.ssh/id_ed25519`, then `ssh-add --apple-use-keychain ~/.ssh/id_ed25519`, and paste the `.pub` file into GitHub [source: GH/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent]. More concepts, but the same key can also sign commits.
- The login itself must be done by the learner in their own Terminal and browser. An AI assistant should never be given a password, token or one-time code, and its sandboxed shell cannot open a browser anyway.
- gh sends pseudonymous telemetry; opt out with `gh config set telemetry disabled` or `export GH_TELEMETRY=false` (`DO_NOT_TRACK=true` also works) [source: GH/github-cli/github-cli/github-cli-telemetry].

### 7.3 gh essentials [source: the CLI/ manual pages named]
- `gh repo create my-project --private --source=. --remote=origin --push` creates the remote from the existing local repository and pushes (CLI/gh_repo_create). `--public` / `--private` is required when non-interactive.
- `gh pr create` (`--fill`, `--draft`, `--title`, `--body`, `--base`, `--label`, `--reviewer`, `--web`), `gh pr view` (`--web`, `--comments`), `gh pr checkout <n>`, `gh pr checks --watch`, `gh pr review --approve | --comment | --request-changes`, `gh pr merge --squash | --merge | --rebase [--delete-branch] [--auto]`.
- `gh issue create` (`--title`, `--body`, `--label`, `--milestone`, `--assignee @me`, `--type`, `--parent`), `gh issue list`.
- `gh run list`, `gh run watch [--exit-status] [--compact]`, `gh run view --log-failed` (the fastest way to read why CI is red), `gh workflow run ci.yml` for `workflow_dispatch`.
- `gh release create`, `gh label create`, `gh secret set NAME` (value is read from a prompt or stdin, encrypted locally), `gh browse`.

### 7.4 Private or public
- Start private. A repository can be made public later; un-publishing does not un-leak anything already cloned.
- Before going public check: commit author e-mails, `authors` in `pyproject.toml`, data files, notebook outputs, API keys and broker or exchange credentials in history, absolute paths that contain the user name.

### 7.5 Never push
- Secrets: `.env`, API keys, tokens, cookies, `*.pem`, `*.key`, cloud and broker credentials.
- Big or private data: market data dumps, `*.parquet`, `*.h5`, model weights. GitHub warns above 50 MiB per file and blocks above 100 MiB; keep a repository under 1 GB if possible [source: GH/repositories/working-with-files/managing-large-files/about-large-files-on-github]. Git LFS on Free: 10 GB storage and 10 GB bandwidth per month [source: GH/billing/reference/product-usage-included].
- Generated things: `.venv/`, `__pycache__/`, `dist/`, tool caches, `.DS_Store`.
- Do commit `uv.lock` and `.python-version`; `uv sync --locked` in CI depends on them.
- `artifacts/gitignore.example` covers these; `git check-ignore -v .env` printed `.gitignore:16:.env  .env` [local].

### 7.6 The signing blocker (finding 1): three ways out
- Per practice repository, no global change: `git config commit.gpgsign false` inside the repo. This is what I did [local].
- Turn it off globally: `git config --global commit.gpgsign false`. Changes the learner's global config, so it is their decision and their command to run.
- Do it properly with SSH signing: create an ed25519 key, `git config --global gpg.format ssh`, `git config --global user.signingkey ~/.ssh/id_ed25519.pub`, add the key on GitHub as a signing key. Best end state, more steps; place it after the account lesson.
- Whichever is chosen, the course text must show the exact error so the learner recognises it.

### 7.7 Practising before an account exists
A local bare repository behaves like a remote [local]:

```text
$ git init --bare -q ../fake-remote.git
$ git remote add origin ../fake-remote.git && git push -u origin main
$ git switch -c feat/log-return && git commit -am "feat: add log_return" && git push -u origin HEAD
$ git switch main && git merge --squash feat/log-return && git commit -m "feat: add log_return (#1)"
$ git log --oneline --graph
* 037a921 feat: add log_return (#1)
* 0a6411a chore: initial project skeleton
```

Push, fetch, branches and a squash merge can all be taught this way; only issues, PR pages and Actions need GitHub.

## 8. Issues, milestones, Projects, Discussions as a light project-management kit

- Issue = one unit of work or one bug. Now also: issue types (defaults `task`, `bug`, `feature`; available to user accounts as well as organisations, up to 25), sub-issues (up to 100 per parent, 8 levels), blocked-by / blocking dependencies [source: GH/issues/tracking-your-work-with-issues/learning-about-issues/about-issues, .../using-issues/managing-issue-types, .../using-issues/adding-sub-issues]. Older tutorials say issue types are organisation-only and use task-list checkboxes for breakdown.
- Milestone = a dated bucket ("v0.2.0") with a progress bar.
- Projects = table, board (kanban) and roadmap views over issues and PRs, custom fields (date, number, single select, iteration), built-in automations such as auto-add and auto-archive, up to 50 fields; lives at user or organisation level, not inside one repository [source: GH/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects]. `gh` needs an extra scope first: `gh auth refresh -s project` [source: CLI/gh_pr_create].
- Discussions = open-ended Q&A, ideas, announcements; an admin enables it per repository; issues can be converted to discussions [source: GH/discussions/collaborating-with-your-community-using-discussions/about-discussions]. No use for a solo private project.
- Minimum viable setup for the learner: default labels, issue types, one milestone per version, one Project board with Todo / In progress / Done. Skip iterations, roadmaps, custom fields, Discussions.

## 10. Pitfalls a beginner will hit (ordered by likelihood)

1. `git commit` fails with the gpg error (half-written signing config, finding 1).
2. Copying a tutorial workflow with `actions/checkout@v3` / `@v4`, `astral-sh/setup-uv@v1`...`@v7`, `setup-python` + `pip install`; or writing `setup-uv@v10`, which does not resolve.
3. CI red with "The lockfile at `uv.lock` needs to be updated" after editing `pyproject.toml` by hand or forgetting to commit `uv.lock`.
4. Passing locally, failing in CI because of an untracked file, a different Python version, or a dependency installed only locally.
5. `on: [push, pull_request]` doubling every run and the bill.
6. Expecting CI to block a merge on a Free private repository.
7. Requiring one approval on a solo repository: authors cannot approve their own PR.
8. Requiring a check from a workflow with `paths:` filters, or a matrix cell name that later changes.
9. Committing `.env`, data dumps or notebook outputs containing keys or account numbers; no server-side protection on a private Free repository.
10. Publishing the personal e-mail through commit metadata or `pyproject.toml` `authors`.
11. `Closes #n` in a PR that targets a non-default branch, or written as `Closes #1, #2` (only the first closes).
12. Continuing to commit on a branch after it was squash-merged, then fighting conflicts.
13. Workflow file not in `.github/workflows/` on the default branch, or YAML indentation errors; `workflow_dispatch` only appears once the file is on the default branch [memory].
14. A project folder inside iCloud-synced Desktop: iCloud can duplicate or evict files in `.git` and `.venv` [memory; another brief covers this].
15. Typing a token into the chat with the AI assistant instead of into `gh auth login`.

## 11. Recommendations for the course

Teach first, in this order:
1. Fix or sidestep commit signing (7.6); make the first commit.
2. Local "fake remote" practice (7.7): push, branch, squash merge, pull.
3. The four local checks as one habit (`ruff check`, `ruff format --check`, `mypy`, `pytest`) before CI exists; CI is then "the same four commands, run by a robot".
4. Account, 2FA, e-mail privacy, `brew install gh`, `gh auth login` (learner's own hands).
5. `gh repo create --private --source=. --push`; read the repository page.
6. Add `ci.yml`; watch a green run; break a test on purpose; read `gh run view --log-failed`; fix.
7. The solo loop (4.5): issue, branch, PR with `Closes #n`, checks, squash merge, delete branch.
8. PR template and two issue forms; default labels; one milestone.
9. Dependabot (`uv` + `github-actions`, weekly, grouped).
10. First release: `uv version --bump`, hand-written `CHANGELOG.md`, tag, `gh release create --generate-notes`.
11. One awareness lesson: what a team adds (rulesets, required checks, reviewers, CODEOWNERS), why SHA pins, what trusted publishing is.

Skip or mention in one sentence: self-hosted runners, reusable workflows and composite actions, `pull_request_target`, merge queue, environments, OIDC to clouds, workflow lockfiles, `cache-mode`, release-please and python-semantic-release, wikis, Pages, Discussions, Renovate, act.

Sensible defaults:
- Private repository, default branch `main`, squash merge only, auto-delete head branches.
- Branch names `feat/...`, `fix/...`, `docs/...`, `chore/...`; PR titles and commit subjects in Conventional Commits form.
- `ci.yml` from 3.4; in a private repository begin with a single Python version.
- Actions pinned by SHA with a version comment, copied from this brief and re-checked on the day the lesson is written (versions here will age within weeks).
- Dependabot weekly, grouped, 7-day cooldown.
- Validation command to teach: `uvx check-jsonschema --builtin-schema vendor.github-workflows .github/workflows/ci.yml`; optional: `uvx zizmor --offline .github/workflows/`.

Plain-Chinese analogies that fit the facts:
- CI: "每次交作业都自动帮你检查的质检员"。workflow / job / step: "流程 / 工位 / 工序"。
- Runner: "GitHub 借给你的一台一次性电脑，干完活就销毁，所以每次都要重新装环境"。
- `uv.lock` + `--locked`: "按配方原样做菜；配方和菜单对不上就拒绝开工，而不是偷偷改配方"。
