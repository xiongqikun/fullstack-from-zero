# 阶段 3：专业开发规范

> **规划用时** 60～90 小时 ｜ **前置** 阶段 2 ｜ **核实日期** 2026-11-19 ｜ 回到[路线图](../../ROADMAP.md)

下面是计划。课的标题、顺序和编号，建课时会按你的真实进度重新排。**这里是下车点一**：三个特别推荐的落脚点里的第一个，学到这里停下，前面的投入也已经单独有用。

## 目标

把“能跑”的小程序变成“经得起别人接手”的正规项目。学会让机器替你把关：自动排版、自动检查、自动测试，每次推送都跑一遍。学会发布：版本号、更新日志（每个版本改了什么的清单）、版本标签。

## 作品

阶段 2 的换算工具 `fx`。从外面看它没变，用法一样；变的是它不容易坏：带上了测试、自动检查和第一个正式版本 `v0.1.0`，你在 GitHub 上能看到这个版本的发布页。

可选的第二个作品：把你手上已有的一个项目（如果有）复制一份，给副本补上同样的保障，原件一个字不动。

## 这个阶段会学到的规范（计划，建课时定稿）

表里只标规则类型，而且是计划；约束力、谁说的、核对日期在建这个阶段时定，写在每条规范的卡片上。表里的英文名字是这些规范的正式名称，学到时再讲；现在把它们当书名看就行。

| 规范 | 规则类型 |
|---|---|
| 项目的基本信息写进 `pyproject.toml` 这个文件（Python 打包规范） | 标准 |
| 依赖（你的程序用到的、别人写的代码）的精确版本锁进锁文件并提交；别处照锁文件原样重建 | 惯例·平台与工具（uv 的官方文档） |
| 代码的排版和检查交给工具，不靠人争论 | 规范·组织（谷歌公开的工程实践）；用哪个工具、开哪些规则是规范·团队约定 |
| 测试跟着改动一起提交；修缺陷先写一个会失败的测试 | 规范·组织（谷歌公开的工程实践和《Software Engineering at Google》） |
| 每次推送、每个合并请求都自动跑检查（持续集成） | 惯例·平台与工具（GitHub Actions 官方文档） |
| 版本号遵循语义化版本 SemVer 2.0.0（一份规定版本号三段数字各表示什么的公开规范） | 惯例·事实标准 |
| 更新日志遵循 Keep a Changelog 1.1.0（一份规定更新日志怎么写的公开规范） | 惯例·事实标准 |
| 配置和密钥放在环境变量（程序启动时从外面带进来的设置）里，不写进代码（《十二要素应用》第三条） | 惯例·事实标准（最初由一家云平台公司 Heroku 的工程师提出，正文 2017 年后没再改过） |
| 第三方依赖定期查已知漏洞，新版本先等几天再用 | 惯例·平台与工具（uv 的官方文档）；这类风险在 OWASP Top 10:2025 里排第三，那份清单是惯例·事实标准 |
| 流水线用到的第三方步骤固定到具体版本，权限只给够用的 | 惯例·平台与工具（GitHub 官方的安全加固指南） |

## 过关方式

作品通过自己那条“完成的定义”命令，并发布了第一个版本；阶段验收做题时不用 AI 帮忙，其中有一道是评审一份 AI 写的改动。

## 前置

阶段 2。

## 规划用时

60～90 小时。

## 怎么学

两个项目。第一个是必做的：把阶段 2 的换算工具 `fx` 变成正规项目。第二个是可选的：抢救一份现成项目的副本。

从这个阶段起，每一课的改动都走“分支、合并请求、检查通过、合并”这一圈。AI 的角色升一级，可以评审你写好的改动。

## 逐课大纲（草案）

**第一部分：把 `fx` 变成正规项目。**

| 课 | 标题 | 一句话的目标 |
|---|---|---|
| 3.1 | 开工前：需求、看板和“完成的定义” | 把要做的事写成带完成标准的任务，摆上看板；同时在做的不超过两件 |
| 3.2 | 一页设计说明和第一条决策记录 | 动手前写下目标、方案和没选的方案；把一个重要的选择连同理由记下来 |
| 3.3 | 项目的身份证 | 读懂项目的说明文件 `pyproject.toml`；代码和测试各放各的文件夹 |
| 3.4 | 依赖与锁文件 | “我要什么”写在一份文件里，“实际装了哪个版本”锁在另一份里；开发用的工具单独成组 |
| 3.5 | 环境可以扔掉重建 | 删掉运行环境，照锁文件原样重建；在另一个文件夹重新取一份代码，证明别人也跑得起来 |
| 3.6 | 自动排版 | 让工具统一代码的版式；排版的改动单独提交，方便别人看 |
| 3.7 | 静态检查 | 不运行程序就能发现的问题；读懂三条发现；哪些可以放心让工具自动改 |
| 3.8 | 给现在的行为拍照 | 整理代码之前，先用测试把“它现在是怎么表现的”钉住 |
| 3.9 | 小步重构：计算归计算，读写归读写 | 每一步只动结构、不动功能，每一步之后重跑测试；整理和加功能不混在一次提交里 |
| 3.10 | 单元测试 | 用手算得出的小例子测一个函数；一道题换几组数；小数比较要留误差；该报错的地方确实报错 |
| 3.11 | 测试的器材与覆盖率 | 临时文件夹、替换掉外部的东西；覆盖率是“手电筒照到了哪里”，照到不等于检查过 |
| 3.12 | 类型检查 | 程序还没运行，就核对“该放数字的地方有没有放了文字” |
| 3.13 | 一条命令跑全部检查 | 排版、静态检查、类型、测试，合成一条命令；这条命令就是“完成的定义” |
| 3.14 | 持续集成 | 每次推送、每个合并请求，GitHub 自动跑同一条命令；故意弄红一次，读运行记录，修好 |
| 3.15 | 流水线自身的安全 | 第三方的步骤固定到具体版本，权限只给够用的；让机器人定期提醒依赖该更新了 |
| 3.16 | 配置与密钥 | 换个环境就要变的设置不写进代码；用一把假密钥演练“泄露之后第一步是作废” |
| 3.17 | 日志 | 用正规的运行记录代替随手的显示：有时间、有轻重、有来源；记录里不出现密钥和个人信息 |
| 3.18 | 错误处理与退出码 | 出错要早、要说清；在入口处统一检查外来的数据 |
| 3.19 | 稳妥的读写与联网 | 等多久算超时、最多重试几次、写文件要么全写完要么不动 |
| 3.20 | 依赖卫生与供应链 | 查已知漏洞；新版本先等几天再用；升级一个依赖的完整流程；看懂许可证 |
| 3.21 | 提交前的自动检查 | 每次在本机提交之前先自动过一遍检查，早一步拦住问题；它可以被跳过，所以真正把关的是推送后在 GitHub 上跑的那一遍 |
| 3.22 | 先写会失败的测试，再修缺陷 | 重现一个真实的缺陷，写出测试让它变红，修好让它变绿 |
| 3.23 | 文档 | README 加“怎么参与开发”一节；给函数写说明；更新日志怎么写 |
| 3.24 | 版本号与发布 | 版本号三段各是什么意思；打上版本标签；在 GitHub 上发布 `v0.1.0` |
| 3.25 | 让 AI 评审你，你评审 AI | 请一个没参与写的 AI 评审你的改动；再评审一份 AI 写的测试，找出“什么都没验”的那几条 |
| 3.26 | 复盘 | 估计与实际；看板回顾；规范自查：哪条没守住，为什么 |
| 3.27 | 阶段验收 | 动手任务（做的时候不用 AI 帮忙）；评审一份 AI 写的改动；讲“为什么这样做”；排一个故障 |

**第二部分（可选）：抢救一份现成项目的副本。** 对象是你手上已有的一个项目（如果有）的一份副本，原件不动。这一部分没有单独的验收，做完和导师一起对照第一部分的同一份清单检查。

| 课 | 标题 | 一句话的目标 |
|---|---|---|
| 3.28 | 安家与第一次提交 | 把项目复制一份到 `~/Developer`；先找密钥和大文件，写好“不拍名单”，再做第一次提交 |
| 3.29 | 先钉住现有的行为 | 给那些不依赖外界的函数补测试；项目里有笔记本文件（把代码、图表和文字混在一起的一种文件）的，从里面搬出一个函数并补上测试 |
| 3.30 | 有选择地上检查 | 先用默认规则过一遍；亲眼看看在一个现成项目上“规则全开”为什么多半是噪音；排版单独提交 |
| 3.31 | 接上流水线并发布 | 同一条检查命令、同一套流水线；给副本打上第一个版本标签 |

## 技术清单（现在看不懂没关系）

- 项目与依赖：`pyproject.toml`、`src/` 布局、`uv.lock`、`.python-version`、`[dependency-groups]`（PEP 735）、`uv sync --locked`、`uv lock --upgrade-package`、`uv version --bump`、`uv build`。
- 排版与静态检查：ruff（`ruff format`、`ruff check`）。建课当天最新是 0.17.5；从 0.16.0 起默认启用约 400 条规则。
- 类型检查：mypy 2.4.1，`strict = true`。
- 测试：pytest 9.2.0、pytest-cov 7.1.0；`parametrize`、`pytest.approx`、`pytest.raises`、`tmp_path`、`monkeypatch`、`capsys`；characterization test 与 golden file；functional core / imperative shell。
- 一条命令：Makefile 的 `make check`（GNU Make 3.81）。提交前钩子：pre-commit 4.7.0（第 3.21 课；它是安全带，流水线上的检查才是气囊）。
- 持续集成：GitHub Actions；`actions/checkout`、`astral-sh/setup-uv`（要写完整版本号或提交号）；`permissions: contents: read`；Dependabot 的 `uv` 生态。
- 配置、日志、错误：`.env` 与 `.env.example`、pydantic-settings、`logging`、自定义异常与 `raise ... from`、退出码、超时与有限重试、原子写入。
- 供应链：`uv audit`（建课当天仍标为实验性）或 `pip-audit`；`[tool.uv] exclude-newer`；许可证；OWASP Top 10:2025 A03 Software Supply Chain Failures。
- 发布：`git tag -a`、`gh release create`、`CHANGELOG.md`、SemVer 2.0.0、Keep a Changelog 1.1.0；决策记录用 MADR 4.0.0 模板。
- 评审：Conventional Comments；给 AI 改动用的红旗清单。
- 规则类型的出处：PyPA 的 pyproject.toml 规范（来自 PEP）；uv 文档（lockfile、`audit`、`exclude-newer`）；Google Engineering Practices（style guide 是权威）；《Software Engineering at Google》测试各章；GitHub Docs（Actions、security hardening for GitHub Actions）；semver.org；keepachangelog.com；12factor.net 第三条（Heroku / Adam Wiggins，没有版本号，2017 年后未改）。
