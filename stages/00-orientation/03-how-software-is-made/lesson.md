## 第 1 站：拆开一个真实的软件（约 35 分钟）

### 概念

这门课从头到尾在做一个产品，默认是**汇率看板**：一个显示人民币汇率的网页。第 0.1 课运行过的 `hello-fx` 是它的种子。这一站先拆开一个做好的样品，看它由哪几块组成。

一个网页产品，可以拆成四块：

- **前端**（front end）：用户直接看到、直接操作的那一块。看板的网页、表格、「查询」按钮，都是前端。
- **后端**（back end）：在别处等着回答前端提问的程序。网页问“EUR 现在换多少人民币”，后端去查，再把答案送回来。后端通常跑在**服务器**（server）上，就是一台一直开着、专门回答别人请求的电脑。
- **数据**（data）：软件要记住的内容，比如每天的汇率。它和程序分开存放。
- **运行环境**（runtime environment）：程序运行时离不开的那些机器、系统和软件。比如你的 Mac、macOS、`python3`、浏览器；上线（放到网上给别人用，第 1.13 课细讲）以后，还有那台服务器。

画成一张图：

```text
  运行环境：这一切跑在哪些机器上、靠哪些软件跑起来
  ─────────────────────────────────────────────────────────

   用户的电脑（浏览器里）               服务器（一直开着的电脑）

   【前端】看得见的网页      问：EUR 多少？     【后端】回答问题的程序
   表格、按钮、图表      ────────────────▶   收到问题，去查数据
                         ◀────────────────
                             答：7.85                 │ 查
                                                      ▼
                                               【数据】存着汇率的文件

  ─────────────────────────────────────────────────────────
```

打个比方：前端是餐厅的大堂和菜单，后端是后厨，数据是库房里的食材，运行环境是店面、水电和燃气。第 0.1 课里照菜谱做菜的厨师 `python3`，在这张大图里也算进运行环境：它和店面、水电一样，是后厨开工之前就得备好的。

这个比方在哪里不成立：餐厅只有一个大堂，网页的前端却在每一位用户的电脑上各跑一份；一个后端可以同时回答成千上万个人；数据可以一模一样地复制很多份，食材不行。

后端的回答开头，通常带一个三位数，叫**状态码**（status code）。`200` 表示成功，`404` 表示没找到。这些数字属于 HTTP（浏览器和服务器之间对话的规则），意思写在一份编号为 RFC 9110 的标准文件里。什么叫“标准”，第 3 站讲。

回到“先想一想”：1 是前端（天气 App 的页面），2 是后端（天气公司服务器上的程序），3 是数据（气温记录），4 是运行环境（你的手机，加上天气公司的服务器）。

#### 4. 让后端回答一个问题

真正的后端，是服务器上一直开着、等网页来提问的程序。这个样品为了不联网，用一条命令模拟网页问它一次。先猜一猜：问它 EUR，它会回答什么？

```zsh

```

你应该看到（数字和日期你的会不一样，练习场每次搭建时随机生成）：

```text

回答：200 OK

```

> 读懂这句：`200 OK` 是状态码，意思是“成功，给你”。第三行是送回来的数据，一对一对地写着“名字: 值”：`cny`（人民币）是 7.85，就是 1 欧元换 7.85 人民币，这是 2026-11-19 的数字。

#### 5. 故意问一个它没有的

样品的数据里没有日元。先猜一猜：问 JPY，会怎样？

```zsh

```

你应该看到：

```text

回答：404 Not Found
数据里没有 JPY 这种货币。
```

> 读懂这句：`404 Not Found` 是状态码，意思是“没找到”。

1. **谁在报错？** 后端程序 `answer.py` 自己。`python3` 正常运行了它，是它在数据里找不到 JPY，用 404 回答你。
2. **关键词是什么？** `404`、`Not Found`。
3. **我刚才敲了什么？** 我问的是 `JPY`，而数据里只有几种别的货币。

以后在浏览器里看到“404”，你就知道：这是对方的后端在说“我这里没有你要的东西”。

## 第 2 站：从想法到上线，工程级差在哪（约 30 分钟）

### 概念

一个软件从想法到上线、再到长期有人用，大致要走这几步，叫软件生命周期（software development life cycle）。这张图看一眼就好：

```text
  需求 ──▶ 设计 ──▶ 开发 ──▶ 测试 ──▶ 发布 ──▶ 运维
   ▲                                              │
   └───────── 用户的反馈、出的新问题，又回到需求 ◀───┘
```

图上的需求（requirements）是写清楚要做什么、做到什么程度算好，测试（testing）是用写好的检查证明程序做得对，运维（operations）是上线以后让它一直好好运行；真实的团队一小步一小步地转很多圈。

这一站真正要记住的是另一件事。只写代码，程序也可能在你电脑上跑起来。**工程级**是在“能跑”之外，再做到五件事：

| 做到 | 意思 |
|---|---|
| **可重复** | 换一台电脑、换一个人，照同样的步骤做，结果一样 |
| **可追溯** | 每一处改动，查得到是谁、什么时候、为什么改的 |
| **可协作** | 别人不用找你问，就能看懂、接手、一起改 |
| **可验证** | 有写下来的检查，谁运行都能证明它做得对（你每站运行的 `check` 就是一种） |
| **可恢复** | 改坏了、删错了，能回到之前好的样子 |

阶段 1 会用 Git（记录文件每一次改动的工具）和 GitHub（存放项目、和别人协作的网站）把这五件一件件做到。

打个比方：在家做菜，“这次好吃”就行；餐厅后厨要求换一个厨师、换一天、换一家分店，端出来的菜都一样，出了问题查得到是哪一步。

这个比方在哪里不成立：菜做坏了只能重做，软件做到可恢复以后，可以一条命令退回昨天的样子。

#### 2. 运行“最终版”

先猜一猜：它会打印出汇率吗？

```zsh
python3 app-final2.py
```

你应该看到（第 3 行的路径里，`/Users/` 后面是你的用户名；第 5 行那串 `~` 和 `^` 标出出错的位置，样子随 Python 版本不同：有的版本全是 `^`，3.9 这样的老版本没有这一行）：

```text
汇率看板 第二版（教程说：需要 Python 3.8）
Traceback (most recent call last):
  File "/Users/你的用户名/Developer/playground/0.3-start/fx-hobby/app-final2.py", line 4, in <module>
    rates = open("/Users/老王/Desktop/汇率.csv", encoding="utf-8").read()
            ~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
FileNotFoundError: [Errno 2] No such file or directory: '/Users/老王/Desktop/汇率.csv'
```

> 读懂这句：`Traceback (most recent call last)` 是“出错经过（最近的一步写在最后）”。`FileNotFoundError: No such file or directory` 是“找不到文件：没有这个文件或文件夹”。

用报错三问读它：

1. **谁在报错？** Python。`Traceback` 开头的一大段，是 `python3` 在运行这个程序时出错的固定格式。
2. **关键词是什么？** 最后一行的 `FileNotFoundError`，和后面那个路径。
3. **我刚才敲了什么？** 我只是运行了程序。问题在程序第 4 行：它要读 `/Users/老王/Desktop/汇率.csv`，这是写这个程序的老王电脑桌面上的文件。你的电脑上没有。

在老王的电脑上，它能跑；换一台电脑，同样的步骤，结果不一样。这就是缺了**可重复**。

#### 3. 那句“需要 Python 3.8”

程序打印的第一行说，教程要求 Python 3.8。看看你的电脑上是哪个版本。`--version` 是“版本”，它是一个选项（第 0.2 课见过，第 1.1 课细讲）：

```zsh
python3 --version
```

你应该看到类似这样（「你的会不一样」：建课时核对用的是 3.14.9，你看到的版本号可能不同）：

```text
Python 3.14.9
```

说法和电脑对不上，先查这条说法是哪年的、它说的版本还有没有人维护。Python 官方的版本页写着：3.8 在 2024-10-07 停止维护，官方不再给它修漏洞（程序里能被人钻空子的缺陷）、出更新（https://devguide.python.org/versions/ ，2026-11-20 打开核对）。

> **旧教程提醒**：以前很多入门教程写“先装 Python 3.8”；现在 3.8 已经停止维护（自 2024-10-07 起）。建课时核对用的 Python 3.14 还在官方维护期内（计划到 2030-10）；更新的 3.15 已在 2026-10-09 发布。你看到的版本可能不同：课程的工具在 Python 3.9 以上都能用。你的版本还在不在维护期，到上面那个版本页对一对；比如 3.9 在 2025-10-31 也停止维护了。阶段 2 起写程序固定用 Python 3.14（阶段 2 的大纲里写着）。

#### 4. 再看工程级的那一份

先猜一猜：`fx-dashboard` 里那个 `tests` 文件夹，运行起来会打印什么？

## 第 3 站：规范的四种来源和约束力（约 30 分钟）

### 概念

这门课的出发点之一，是讲清楚“规范、标准、行业要求、惯例”这几个词。课程把它们拆成两个问题，遇到一条规矩，分开问：

1. **谁定的？** 叫**规则类型**（rule type）。
2. **有多强制？** 叫**约束力**（obligation level）。

先说规则类型。这四个词对应七种来源：

| 常说的词 | 规则类型 | 是什么 | 打个比方 |
|---|---|---|---|
| 标准 | **标准**（standard） | 标准组织正式发布、带编号的文件 | A4 纸的尺寸（推荐性国家标准 GB/T 148-1997）：没人逼你用，但不按它做，打印机、复印机、文件夹就都和你对不上 |
| 行业要求 | **行业要求**（compliance requirement） | 法律、法规、合同、审计（第三方来检查你做得合不合规）、平台的强制政策：第三方能拿它追究你 | 交通法规和营业执照：不遵守会被罚、被下架、丢合同 |
| 惯例 | **惯例**·事实标准 | 公开、写明版本、很多互不相干的项目和工具都照着做的社区规范，比如语义化版本（规定软件版本号怎么写） | 书信开头写称呼、结尾写“此致敬礼”：没有法律规定，但大家都这么写 |
| 惯例 | **惯例**·平台与工具 | 某一个工具或平台本来就这么工作、这么期待 | 小区和商场的规定：在人家的地盘上，按人家的方式来 |
| 规范 | 规范·组织 | 一家组织给自己的工程师写的规矩，外人自愿采用，比如 Google 的风格指南（规定代码怎么排版、怎么命名的手册） | 公司的员工手册、后厨操作规程 |
| 规范 | 规范·团队约定 | 这个团队、这个仓库（被 Git 管着的项目文件夹）自己定的；只因为本课程这样选才有的，写成规范·本课程约定 | 合租公约：自己人商量定的，可以改，但定了就要守 |
| （都不是） | **个人偏好**（personal preference） | 不是规则，可以自己决定 | 口味：可以坚持，但不能拿来要求别人 |

这些比方在哪里不成立：软件里的规矩大多写成了文字、标了版本和日期，生活里的这些不一定。

**惯例**（convention）合起来说，就是没人能罚你，但工具和同行都默认你这么做。日常中文里“规范”也常被当成所有这些的总称；在规则卡片上，它只指表里那两类成文的规矩。

再说约束力。分三级，括号里写适用范围（本课程、本机、所在团队或所有项目）：

| 约束力 | 意思 |
|---|---|
| **必须** | 违反会造成真实的损害、操作被拦下，或者违法违约 |
| **推荐** | 照做，除非你说得出理由 |
| **参考** | 知道就好，自由选择 |

这两个问题互不相干。例子：**约定式提交**（Conventional Commits，1.10 课学）是一份社区规范，规定提交说明（用 Git 保存一个版本时写的那句话）怎么写，本身是推荐（适用范围：所有项目）。一个团队设了自动检查，不按它写的提交会被拦下，在这个团队里它就是必须（适用范围：所在团队）。类型没变，变的只是约束力。合同点名也一样：合同里写“必须符合某某规范”，那一条合同条款对你是行业要求；被点名的规范类型不变，只是在那个项目里成了必须。

给一条规矩分类，用**七步判断法**：按顺序问，遇到第一个“是”就停。问的都是这条规矩本身从哪来。

1. 监管机构、法院、客户、审计方或平台，能因为我不遵守它而罚我、追究我、封我的账号吗？是，就是**行业要求**。工具只是报错、不干活，不算惩罚，那是第 4 步。
2. 发布它的是标准组织吗？名单是固定的：ISO/IEC（国际标准化组织和国际电工委员会）、IETF（发布叫 RFC 的技术文件）、W3C 和 WHATWG（网页标准）、Ecma（发布 JavaScript 这门网页编程语言的标准）、Unicode 联盟（给世界上的文字统一编号）、Python 指导委员会（批准 PEP，带编号的 Python 改进提案）、国家标准委（发布 GB 标准）。这样的文件带编号（RFC 9110、PEP 8）。是，就是**标准**。
3. 它是公开发布、写明版本或日期、很多互不相干的项目和工具都照着做的规范或框架，而且不是某一家组织以自己名义写给自己人的吗？是，就是**惯例·事实标准**。
4. 它只是某一个工具或平台本身的工作方式或期待吗（包括它在自己的官方文档里教你怎样用它）？是，就是**惯例·平台与工具**。
5. 它是某一家组织以自己的名义写的做法指南吗？是，就是**规范·组织**。
6. 它是这个团队、这个仓库（包括本课程）自己定的吗？是，就是**规范·团队约定**。
7. 都不是，那就是**个人偏好**。

分好类，再单独问一次：在我今天的处境里，它是必须、推荐还是参考？

#### 3. 跟着七步判断法分一句

「提交说明以 `feat:` 或 `fix:` 开头。」（`feat:` 表示新增了一个功能，`fix:` 表示修了一个问题，第 1.10 课细讲。）

- 第 1 步：有谁能因为这个罚你吗？没有。
- 第 2 步：发布它的是名单里的标准组织吗？不是。
- 第 3 步：它出自公开的“约定式提交 1.0.0”，有版本，很多项目和工具照着做。是，停。

它是**惯例·事实标准**。约束力：推荐（适用范围：所有项目）；1.10 课起 必须（适用范围：本课程）。

#### 4. 一条“规矩”，真的是规矩吗

很多教程说：“提交说明的第一行不能超过 50 个字符，这是 Git 的规定。”先问：这是 Git 自己写的吗？

`git commit` 的说明书（man page，第 0.2 课学过）DISCUSSION 一节说：第一行写一句不超过 50 个字符的摘要，不是必须的，但是个好主意（Git 官网上的同一份说明书 https://git-scm.com/docs/git-commit ，2026-11-20 打开核对：这一页最后改动于 Git 2.55.0；建课时核对的 Git 2.54 自带的说明书里这句话一字不差）。

不问出处，就会把“好主意”当成“必须”，也会把真正的“必须”当成随便听听的建议；不记版本和日期，就会照着过时的说法做。这就是本课行规要防的事。

> **旧教程提醒**：以前很多教程把这 50 个字符说成 Git 的硬性规定；现在 Git 的说明书说它不是必须的，至少从 2014 年的 Git 2.0.5 起就一直这么说（当时写的是少于 50 个字符，后来改成不超过 50 个）。

> **想多了解（可跳过）：GB 和 GB/T**
> 中国国家标准的编号前缀写着约束力：GB 是强制性国家标准，GB/T 是推荐性国家标准。家里的插头插座是 GB 1002-2024，强制性的，2025-08-01 起实施：不符合强制性标准的产品不得生产、销售，这是《标准化法》第二十五条说的。A4 纸的尺寸是 GB/T 148-1997，推荐性的。软件里常听到的“等保 2.0”是 GB/T 22239-2019（网络安全等级保护基本要求），也带 /T，是推荐性的；客户在合同里写明系统必须达到它，对那个项目它就成了必须，它还是标准。三项的状态都在国家标准全文公开系统查得到（https://openstd.samr.gov.cn/ ，在首页搜标准号，比如 22239；2026-11-20 打开核对：GB 1002-2024 强标、现行，GB/T 148-1997 和 GB/T 22239-2019 推标、现行）。

> **想多了解（可跳过）：必须、推荐、参考从哪来，规矩怎么引用**
> “必须、推荐、参考”对得上英文技术规范里大写的 MUST、SHOULD、MAY。这三个词的确切意思由 IETF 的 RFC 2119（1997 年 3 月）定义，2017 年 5 月由 RFC 8174 补充（https://www.rfc-editor.org/info/rfc2119 ，2026-11-20 打开核对）。RFC 2119 用到今天快三十年了：有的规范多年不变，平台政策和法律却老得快。所以引用一条规矩，要说得出出处、哪一版、哪一节，比如“RFC 9110 第 15.5.5 节”“语义化版本 2.0.0”，每张规则卡片也都写着哪天核对的、多久复核一次。
